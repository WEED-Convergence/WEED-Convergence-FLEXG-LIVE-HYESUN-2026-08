# CONVERGENCE Docs — 팀원 가이드 & 작성 지침

이 저장소(**CONVERGENCE Docs**)로 기획 프로토타입을 만들고 문서화하는 팀원이 **처음부터 끝까지** 보는 문서.
AI 협업용 지침(저장소 루트 `CLAUDE.md`)과 같은 규칙을 공유한다. 헷갈리면 이 문서 → `CLAUDE.md` 순서로 본다.

---

## 0. 이게 뭔가요 · 누가 쓰나

- **무엇** : 한 화면(실제 UI 프리뷰) + 그 화면 설명 + 화면 위 번호 마커 + 피그마식 코멘트를 트리로 묶은 **기획 문서 포맷**. 표준 컴포넌트로 화면을 "조립"해 프로토타입을 만든다.
- **누가** : 기획·디자인·퍼블리싱·개발이 **같은 화면·같은 컴포넌트**를 보고 협업. 비개발자도 읽는다(용어를 쉽게 쓰는 이유).
- **두 축** :
  | 축 | 위치 | 성격 |
  | --- | --- | --- |
  | 기획 문서(docs) | `/docs` | 프로젝트별 화면 스펙(이 저장소에서 계속 새로 쓰는 것) |
  | 디자인 시스템(컴포넌트북) | `/components` | 서비스별 표준 컴포넌트·토큰(별도로 자라는 것) |

---

## 1. 빠른 시작 (5분)

```bash
npm install          # 최초 1회
npm run dev          # http://localhost:3000
```

접속 경로:
| 경로 | 내용 |
| --- | --- |
| `/docs` | 기획 문서 셸(좌 트리 · 중앙 프리뷰 · 우 설명) |
| `/docs/overview` | 이 프로토타입 개요(표지) |
| `/docs/pages` | 작업페이지 한눈에 보기(화면 인덱스) |
| `/components` | 컴포넌트 표준(디자인 시스템) |
| `/preview/<id>` | 개별 프리뷰 화면(iframe 안에서 렌더되는 실제 UI) |

> **Claude Code로 시작하면** 위를 외울 필요 없다. 그냥 "새 화면 만들래" 라고 하면 Claude가 서비스 → 페이지를 물어보고 표준 컴포넌트로 시작해준다(아래 8·CLAUDE.md 참고).

## 2. 화면 구성 이해 (3분할)

| 영역 | 내용 | 소스 |
| --- | --- | --- |
| 좌측 | 그룹 → 페이지 → 팝업 트리 · 검색 · 「작업페이지 한눈에 보기」 진입 | `src/docs/DocsShell.tsx` |
| 중앙 | 실제 화면 프리뷰(iframe) + 번호 마커 + 코멘트 핀 + 탭 | `DocsShell` + 프리뷰 화면 |
| 우측 | 화면 설명 — 공통 개요 · 구성(섹션=마커) · 상태별 표 · 사용된 컴포넌트 | `DocsShell` |

- **프리뷰**는 진짜 UI(`src/preview/screens.tsx`)를 iframe으로 띄운 것. 표준 컴포넌트로 조립한다.
- **마커**는 프리뷰의 특정 요소와 우측 설명을 번호로 1:1 연결한다.
- **코멘트**는 화면 위에 핀으로 남기는 피드백(아래 7).

## 3. 새 화면(기획서 한 장) 추가 절차

1. **프리뷰 화면을 만든다** — `src/preview/screens.tsx`에 실제 UI를 그린다.
   - 표준 컴포넌트는 `src/design-system`(배럴)에서 가져온다. (아래 4)
   - 설명과 이을 요소에 `data-doc-mark="키"`, 탭이 있으면 컨테이너에 `data-doc-tab="탭명"`.
   - `/preview/<id>` 라우트에 렌더되게 `screens.tsx`의 `DemoScreen` 분기에 연결.
2. **카탈로그에 등록** — `src/docs/catalog.ts`의 `DOC_GROUPS`에 `DocEntry` 추가.
   - `id·code·name·route·breadcrumb·type·summary·common·sections·status` 등.
   - `sections[].mark`를 프리뷰의 `data-doc-mark` 값과 **일치**시키면 번호 마커가 자동으로 얹힌다.
3. **상태 지정** — `status: '작성중' | '검토중' | '확정'` → 「작업페이지 한눈에 보기」에 뱃지로 표시.
4. **확인** — `npm run dev`에서 `/docs/<id>` 로 보고, 마커·설명이 맞물리는지 점검.

> 셸(`DocsShell`) 레이아웃 코드는 건드리지 않는다. **데이터(카탈로그) · 프리뷰 화면 · 컴포넌트**만 채운다.

## 4. 컴포넌트 사용 — 표준을 먼저, 없으면 임시조립 + 요청

- **표준 컴포넌트를 먼저 쓴다.** 화면 조립 시엔 **deep import 하지 말고 공개 배럴 `src/design-system`으로만** 가져온다.
  ```tsx
  import { AdminLayout, StatCard, InfoCard, colors } from '../design-system';
  ```
  배럴에 없으면 `src/design-system/index.ts`에 export를 추가한다.
- **표준에 없는 컴포넌트가 필요하면** 프로토타입 안에서 **임시로 조립**하되, 설명(섹션 body)에 「표준 컴포넌트 미적용 — 디자인시스템 요청 대상」으로 남긴다.
- **⚠️ 프로토타입 작업자는 만든 것을 컴포넌트화·갤러리 등록하지 않는다.** 정식 컴포넌트 추가는 **디자인 시스템 트랙(별도 업데이트/레포)** 의 일이다. (`/components`는 "무엇이 있는지 확인하는" 용도)

## 5. 작성 규칙 (반드시 지킴)

### 5-1. 문장 — 명료 선언형
읽는 사람에 비개발자(디자인·마케팅·영업)도 있다. 짧고 분명하게.

| 규칙 | 나쁜 예 | 좋은 예 |
| --- | --- | --- |
| 줄글 대신 간결 선언형(명사형·"~함") | 고객이 입장하면 닉네임을 물어봅니다. | 입장 시 닉네임을 1회만 등록함 |
| 항목이 여럿이면 `1) 2) 3)`으로 나열 | 카드로 요약하고 클릭하면 상세로 갑니다 | 1) 카드로 요약함<br>2) 클릭 시 상세로 이동함 |
| 코드 식별자·내부 용어 금지 | `state=live`일 때 `LiveSettingsV2` 노출 | 방송 중일 때 설정 화면 노출 |

- 강조(빨강/굵게)는 한 항목에 **1~2곳만**.

### 5-2. 표 — 가능하면 무조건 표
탭 구성·컬럼·상태별 동작·매핑처럼 **축이 둘 이상**이면 줄글로 풀지 말고 표로.
- 상태(로그인 전/후·권한 등)별 차이는 `stateTable`로.
- **문서 표는 항상 직사각형**(라운드 없음). 항목이 많을 수 있으니 **내용은 셀로 분리**해 쓴다.

### 5-3. 설명 — 기능 정의·예외 케이스 (컴포넌트는 분리)
섹션 `body`엔 **기능 정의·규칙·예외 케이스**(무엇을 하고, 언제 어떻게 다르게 동작하는지)를 쓴다.
- 컴포넌트명·색·px 같은 **구현 디테일은 body에 쓰지 않는다.**
- 실제 쓴 표준 컴포넌트명은 `components: [...]`로 **분리** → 각 섹션 아래 「사용된 컴포넌트」로 노출.
```
✕  body: 주문 상태별 건수를 지표 카드(StatCard)로 나열함
○  body: 1) 주문 상태별 처리 필요 건수를 요약
        예외) 처리할 건이 없으면 0으로 표기(숨기지 않음)
   components: ['SectionHead', 'StatCard']
```

### 5-4. 마커 · 공통
- 프리뷰 요소 `data-doc-mark="키"` ↔ 섹션 `mark:"키"`로 번호 연결. 번호는 화면 좌표(위→아래) 자동.
- 마커는 요소 **왼쪽 위 모서리** 원형(마커=분홍, 코멘트 핀=파랑).
- 마커로 못 찍는 개요·전제·공통 규칙은 **공통(common)** 에 쓴다(항상 노출).
- 새 화면은 항상 **공통 개요 + 구역별 마커 섹션**을 갖춘다.

### 5-5. 변경 프레이밍 금지 · 기타
- 확정 배포 외에는 `기존 A→B/개편/변경` ✕ → **현재형** 스펙 서술 ○. (배포월/릴리즈/변경종류 개념 없음)
- UI에 **이모지 금지** — SVG 아이콘 컴포넌트로.
- 색상·간격·개발 URL 등 디자인/구현 디테일은 설명에 쓰지 않는다.
- 페이지를 수정하면 `updatedAt`(변경일)을 **수정한 날짜**로 갱신.

## 6. 상태 & 작업페이지 한눈에 보기

- 각 화면의 `status`(작성중 → 검토중 → 확정)로 진행도를 표시.
- `/docs/pages`(좌측 「작업페이지 한눈에 보기」)에서 **영역별 화면 목록 + 상태**를 한눈에 본다. (배포 이력이 아니라 화면 인덱스)

## 7. 코멘트 (피드백)

- 프리뷰 화면을 클릭해 **핀**으로 코멘트를 남긴다(피그마식). 우측 「코멘트」 탭에서 목록으로 본다.
- 저장은 브라우저 `localStorage`(내 브라우저 한정). 팀 공유가 필요하면 `src/docs/commentStore.ts`만 원격 백엔드로 교체(공개 API 동일).

---

## 8. 작업 올리기 — 브랜치 + PR

- **main 직접 push 금지.** 항상 작업 브랜치 → PR로만 머지.
  ```bash
  git checkout main && git pull
  git checkout -b feat/<작업명>
  # ...작업...
  git push -u origin feat/<작업명>   # 출력의 pull/new 링크로 PR 생성
  ```
- 커밋/PR은 **관련 변경을 모아서** 한 번에. 기능마다 잘게 쪼개지 않는다.
- `node_modules`·`tsconfig.tsbuildinfo`·스크린샷 등은 커밋하지 않는다(`.gitignore`).

## 9. 자주 겪는 헤맴 (FAQ)

| 증상 | 해결 |
| --- | --- |
| 뭘 먼저 해야 할지 모르겠다 | Claude Code에 "새 화면 만들래" → 서비스·페이지 질문에 답하고 시작(아래) |
| 마커 번호가 안 붙는다 | 프리뷰 `data-doc-mark` 값과 섹션 `mark` 값이 **정확히 같은지** 확인 |
| 프리뷰가 "알 수 없는 프리뷰"로 뜬다 | `screens.tsx`의 `DemoScreen` 분기에 `case '<id>'`를 추가했는지 |
| 컴포넌트가 없다 | 임시 조립 + 설명에 「디자인시스템 요청 대상」 표기(직접 컴포넌트화 X) |
| 화면이 안 뜬다 | `npm install` 후 `npm run dev`, 콘솔 에러 확인 |

> **Claude Code 온보딩** : 이 저장소를 받아 Claude Code를 열면, "무엇을 하실 건가요?"로 시작한다 → 새 화면이면 **① 어떤 서비스? ② 어떤 페이지?** 를 묻고 그 표준 컴포넌트로 조립을 시작한다. (상세: 루트 `CLAUDE.md`)
